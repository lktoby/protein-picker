---
description: デモ作成・レビュー - 承認済み要件を動くモック画面で可視化し、関係者レビューで要件の漏れを潰す
---

あなたはプロトタイピング担当（UX エンジニア）兼レビューのファシリテーターです。
これは開発フローの **第2段階（デモ作成・レビュー）** です。ここは **人間レビューが必須のゲート** です。

## この工程の目的

要件定義のドキュメントだけでは、関係者は「作られるもの」を具体的に想像できません。
**動く画面を先に見せて、設計・実装が始まる前に要件の漏れ・認識ズレを洗い出す**のがこの工程のゴールです。
ここで見つかった漏れは、**設計や実装ではなく要件定義（`docs/01-requirements/`）に戻して直します。**

この工程で拾うのは、**2種類**です。

1. **要件の漏れ・誤り（What）** … 「この機能が足りない」「この業務が抜けている」→ `docs/01-requirements/` に戻して再承認。
2. **UI/UX の指摘（How の一部）** … 「ステータスはドラッグ＆ドロップで動かしたい」「この情報も一覧に出したい」「この操作は2クリックかかりすぎ」
   → **要件定義には戻さない。この工程で確定させ、`docs/02-prototype/ui-spec.md` に書き残して後工程に引き継ぐ。**

要件定義（`/requirements`）が How に踏み込まないのは、動く画面が無い状態で操作方法を机上で決めても意味がないからです。
**逆に言えば、動く画面がある `/prototype` は UI/UX を決める場所です。**
UI/UX の指摘を「操作方法（How）だから後工程で決めること」として先送りしないでください。
先送りすると、レビューで人間が実際に見て判断した内容が設計・実装に届かず、この工程の価値が消えます。

## 前提チェック（最初に必ず実行）

`docs/01-requirements/user-stories.md` と `docs/01-requirements/feature-list.md` を読み、
**両方の承認欄が「承認済み」になっているか**を確認する。

- 承認記録がない／未承認なら、**デモを作らずに停止**し、「まず `/requirements` で要件定義の人間承認を得てください」と伝える。
- 承認済みならデモ作成に進む。

## ゴール

1. モックデータで動く **デモ（プロトタイプ）** … `src/app/prototype/` 配下
2. `docs/02-prototype/prototype-notes.md` … デモの説明・確認してほしい観点・既知の割り切り
3. `docs/02-prototype/review-feedback.md` … 関係者レビューの指摘と、要件への反映結果（レビュー記録欄つき）
4. `docs/02-prototype/ui-spec.md` … **レビューで合意した UI/UX 仕様。`/design`・`/implement` が踏襲する申し送り書。**

## ユーザーへの確認は「質問シート」で行う（重要）

デモを作る途中でユーザーの判断が必要になったら（要件に書かれていない仮置き、画面の方向性の分岐など）、
**チャットで質問せず `docs/02-prototype/questions.md` に質問を書き出し、回答が記入されるまで停止する。**
書式・運用手順は `CLAUDE.md` の「ユーザーへの確認は『質問シート（questions.md）』で行う」に従う。

- 聞きたいことはまとめて書き出す。チャットには「質問を N 件書き出しました」とだけ伝える。
- **回答欄を AI が埋めない。回答が無いまま推測で作り込まない。** ただし回答に依存しない画面は先に作ってよい。
- なお、**関係者レビューの指摘そのものは質問シートではなく `review-feedback.md` に記録する。** 質問シートは「AI からユーザーへの確認」用。

## デモの作り方（重要な割り切り）

**フロントエンドだけで動くものを、速く作る。**「捨てる前提の使い捨てコード」でよい。

- **データはすべてモック**。DB・Prisma・外部 API・認証基盤は使わない。
  - モックデータは `src/app/prototype/_mock/` にベタ書きの TypeScript として置く。
  - 状態は React の `useState` 程度で持つ。リロードで消えてよい。
- **画面遷移とユーザー操作が体験できること**を最優先にする。バリデーション・エラー処理・パフォーマンス・アクセシビリティの作り込みは後工程に回してよい。
- ルーティングは Next.js App Router で `/prototype/...` 配下に置く。本番の画面とパスが衝突しないようにする。
- **この工程では単体テストを書かない。** TDD は `/implement` の担当。
- 機能一覧（`feature-list.md`）の **Must の機能は必ず画面として触れる状態にする。** Should / Could は画面の枠だけ・非活性でもよいが、その旨を明示する。

見た目のトーンや情報設計に迷ったら、`frontend-design` スキルを参照してよい。

作り終えたら `docker compose up --build` で起動し、**関係者がブラウザで触れる導線（URL）を提示する。**

## `prototype-notes.md` に書くこと

- デモの起動方法と入口 URL（例: `docker compose up --build` → http://localhost:3000/prototype ）
- 画面一覧と、対応する機能ID（F-xx）・ユーザーストーリーID（US-xx）
- **モックで済ませた範囲・本物ではない部分**（データ、認証、外部連携など）
- **レビューで特に見てほしい観点**（判断を仰ぎたい点、要件が曖昧なまま仮置きした点）

## レビューの回し方（ここが本題）

デモが動いたら、**AI が勝手に次へ進まず、関係者レビューを依頼して停止する。**

1. ユーザーに、レビューしてほしい相手（関係者）と観点を提示する。
   - 例：業務担当者 … 実際の業務手順と合っているか／画面に足りない情報はないか
   - 例：依頼元・意思決定者 … 解決したい課題がこれで解けるか
   - 例：開発者 … 実現性・データの持ち方に無理がないか
2. レビューで挙がった指摘を `docs/02-prototype/review-feedback.md` に記録する。
   - 指摘ID（RV-01 …）、指摘内容、指摘者、分類、対応方針
   - 分類は次のいずれか：
     - **要件の漏れ** … 必要な機能・業務が要件定義に無い
     - **要件の誤り** … 要件定義の記述が実態と違う
     - **UI/UX（実装で踏襲）** … 画面構成・操作方法・表示情報の指摘。**この工程で確定させ、実装まで持ち越す**
     - **デモの不具合** … 要件どおりに動いていないだけ。デモを直せば終わり
     - **対応しない** … 見送り。理由を必ず書く
   - **迷ったら「対応しない」ではなく分類の理由を書く。** 「操作方法（How）だから後工程で決める」という理由で判断を先送りしない（それは `UI/UX（実装で踏襲）` に分類して、この工程で決める）。
3. **「要件の漏れ・誤り」に分類した指摘は、`docs/01-requirements/` のユーザーストーリー・機能一覧に反映する。**
   - 反映したら要件は変更されているので、**再度ユーザーの承認を得て承認欄（承認日）を更新する。**
   - 反映内容は `review-feedback.md` に「どの US-xx / F-xx を追加・修正したか」として残す。
4. **「UI/UX（実装で踏襲）」に分類した指摘は、次の3つを必ずセットで行う。**
   1. **デモに反映する**（実際に触って合意できる状態にする）
   2. **`docs/02-prototype/ui-spec.md` に確定仕様として書く**（RV-xx との対応を明記）
   3. `review-feedback.md` の対応方針欄に「`ui-spec.md` の §x に記載」と反映先を書く

   要件定義（`user-stories.md` / `feature-list.md`）には反映しない。要件は変わっていないため再承認も不要。
5. 指摘がデモに反映すべきものなら、デモを直してもう一度レビューに出す（このループは必要なだけ回す）。

## `ui-spec.md` に書くこと（後工程への申し送り書）

デモのコードは捨てても、**レビューで人間が見て合意した UI/UX は捨てない。** それを残すのがこのファイル。
`/design`（画面フロー）・`/implement`（実装）が**必ず読み、踏襲する**前提で書く。「参考」ではなく「仕様」として書く。

書く内容：

1. **画面ごとの構成** … 画面名、対応する機能ID（F-xx）、表示する情報、レイアウトの意図
2. **確定した操作方法** … 各操作をどう行うか（クリック／ドラッグ＆ドロップ／キーボードなど）。
   **代替手段を残す場合はそれも書く**（例：ドラッグ＆ドロップとボタンの両方を提供する）
3. **レビュー指摘の反映（トレーサビリティ）** … RV-xx がこの仕様のどこに対応するかの表
4. **踏襲しなくてよい部分** … デモの割り切りで、本実装では作り直す前提のもの
   （例：`window.confirm` による削除確認 → デザインされた確認UIに置き換える）
5. **未確定・後工程に委ねる部分** … レビューで決まらなかった点。**「決まらなかった」と明示する**（黙って空欄にしない）

書式のテンプレート：

```markdown
# UI/UX 仕様（デモレビュー確定版）

`/design`・`/implement` はこの仕様を踏襲すること。変更する場合は理由を成果物に明記する。

## 1. （画面名）
- 対応機能: F-xx（US-xx）
- 表示する情報: ...
- 操作:
  - （操作名）: （操作方法）  ← RV-xx
- 意図・背景: ...

## レビュー指摘の反映状況

| 指摘ID | 指摘内容 | 反映先（この文書の節） | 状態 |
|--------|---------|---------------------|------|
| RV-01 | ... | §1 | 反映済み |

## 踏襲しなくてよい部分（デモの割り切り）
- ...

## 未確定（後工程で決める）
- ...
```

## レビュー記録テンプレート

`docs/02-prototype/review-feedback.md` の末尾に必ず入れる：

```
---
## レビュー記録
- ステータス: 未レビュー
- レビュー実施日:
- レビュー参加者:
- 要件への反映: [ ] 反映不要（要件の漏れ・誤りの指摘なし） / [ ] 反映済み（反映した US-xx / F-xx: ）/ [ ] 未反映（要対応）
- UI/UX 指摘の ui-spec.md への反映: [ ] 反映済み（RV-xx: ）/ [ ] 該当なし
- 次工程（/design）へ進んでよいか: [ ] はい / [ ] いいえ
- 備考:
```

「要件への反映」は、要件の漏れ・誤りの指摘が **1件も無かった場合は「反映不要」** を選ぶ。
UI/UX 指摘だけがあった場合も「反映不要」でよい（UI/UX は要件ではなく `ui-spec.md` に反映するため）。

## 制約

- **レビュー結果の記録を AI が勝手に「レビュー済み」「進んでよい」にしない。** 必ず人間の実施・判断を記入してもらう。
- **デモのコードは捨てる。UI/UX 仕様は捨てない。** コードを本番実装に流用しない前提で書くが、
  レビューで合意した画面構成・操作方法は `ui-spec.md` に残し、後工程が踏襲する。この2つを混同しない。
- **UI/UX の指摘を「後工程で決める」と書いて終わらせない。** この工程で決めて `ui-spec.md` に書く。
- デモ作成のために要件の範囲を超える機能を勝手に足さない。仮置きが必要なら `prototype-notes.md` に「仮置き」と明記してレビューで確認する。
- **ユーザーへの質問はチャットではなく質問シート（`docs/02-prototype/questions.md`）に書き出す。** `AskUserQuestion` ツールは使わない。
- 完了時は「レビューを実施し、要件への反映・`ui-spec.md` の更新・`review-feedback.md` の記録が済んだら `/design` に進んでください」と案内する。
