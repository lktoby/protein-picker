# ユーザーストーリー — プロテイン比較・購入アプリ（仮称）

- 作成日: 2026-08-27
- 根拠: `docs/01-requirements/questions.md`（ラウンド1・2 の回答）
- 位置づけ: 開発フロー第1段階（要件定義）の成果物。**何を作るか（What）** までを扱い、技術・設計（How）は後工程で決める。

## 1. プロダクト概要

| 項目 | 内容 |
|------|------|
| テーマ | プロテインの比較・購入アプリ（Q-01） |
| 解決したい課題 | プロテインは種類・機能が多く、初心者が目的に合う商品を選ぶには調べる知識が多すぎる。目的に応じて初心者でも選びやすくする（Q-03） |
| 対象ユーザー | 主: プロテイン初心者 ／ 副: プロテイン経験者（検索・情報の一気見は経験者も使う）（Q-03, Q-04） |
| 利用シーン | 「プロテインを買うか悩んでいる」タイミングでスポット的に使う（Q-06） |
| 前提 | モックアプリとして作る。**個人情報の入力を求めない・誘導しない**（Q-02, Q-05）。商品データは主要な種類をカバーする 10〜20 件程度のサンプルデータ（Q-11） |

## 2. ユーザーストーリー一覧

優先度: Must（必須）／ Should（できれば）／ Could（余裕があれば）

### US-01（Must）目的・条件を選びたい
> プロテイン初心者として、飲む目的（例: 筋肉をつけたい・ダイエット・健康維持）、飲みたいタイミング（例: 運動後・朝・就寝前）、その他のこだわり（例: 乳糖不耐症（lactose intolerant）対応）を選択肢から選びたい。なぜなら、専門知識がなくても「自分の状況」を伝えるだけで商品選びを始められるようにしたいから。（Q-01, Q-04）

### US-02（Must）条件に合うおすすめを理由付きで見たい
> プロテイン初心者として、選択した条件に合うおすすめ商品を、おすすめ順に 1 件ずつ順番に見ていきたい。各商品には写真・ブランド・値段・1g あたりの価格と、「なぜおすすめか」の 1 行の理由が添えられていてほしい。なぜなら、知識がなくても納得して選べるようにしたいから。（Q-04, Q-07）

- 補足（UI/UX 要望メモ）: カード形式・カルーセル表示という具体的な見せ方の要望あり（Q-07）。表示方法の確定は `/prototype` の `ui-spec.md` で行う。
- 補足（How の扱い）: おすすめの計算の仕組み（外部 AI API か、ローカル計算か）は `/design` で決定する（Q-07 の AI 補足参照）。

### US-03（Must）商品を検索したい
> プロテイン初心者・経験者として、商品名やブランド名で商品を検索したい。なぜなら、気になっている商品や聞いたことのある商品を直接調べたいから。（Q-04, Q-10）

### US-04（Must）商品情報を一気見したい
> プロテイン初心者・経験者として、商品ごとに、値段（1g あたりの価格）・タンパク質の含有率などの情報と、販売場所（ネット通販・実店舗）の一覧を 1 か所でまとめて見たい。なぜなら、複数のサイトや店舗を自分で調べて回る手間をなくしたいから。（Q-01, Q-04）

### US-05（Must）アプリ内で購入を完了したい（ネット通販）
> プロテイン初心者・経験者として、ネット通販で売られている商品を、アプリを出ずにそのまま購入手続きして買いたい。支払いはダミーの情報で行う（実在の個人情報・支払い情報は入力しない）。なぜなら、選んだ流れのまま迷わず購入まで完了したいから。（Q-01, Q-04, Q-05, Q-08）

- 補足: 購入画面にダミーの支払い入力フォームを置き、架空の値（またははじめから入っているダミー値）で購入を確定する。入力値は個人情報として扱わず保存しない（Q-12）。

### US-06（Must）注文履歴を見たい
> 購入したユーザーとして、注文履歴画面で自分が注文した商品を確認したい。なぜなら、何をいつ買ったかを後から見返したいから。（Q-01, Q-04, Q-09）

- 補足: アカウント登録・ログインは作らない。履歴は「このアプリで注文したもの」として表示する（Q-09）。
- 補足（How の扱い）: 注文をデータベースに保存し履歴画面で読み出す構成の要望あり（Q-09。PostgreSQL の利用に言及）。データ保存方式の確定は `/design` で行う。

### US-07（Must）購入した商品について問い合わせたい
> 購入したユーザーとして、商品が届いた後などに、その商品の販売店舗のお問い合わせ先（メールアドレス・電話番号）を注文履歴などから確認したい。なぜなら、商品に不明点や問題があったときに、どこへ連絡すればよいかすぐ分かるようにしたいから。（Q-01, Q-04）

- 補足: モックのため実際のメール送信・発信は行わない（連絡先の表示まで）。

### US-08（Must）実店舗の情報を見たい
> プロテイン初心者・経験者として、実店舗で売られている商品について、その店舗の販売価格・アクセス方法・連絡先を見たい。なぜなら、店頭で買う場合にどの店へ行けばよいか判断したいから。（Q-01, Q-04）

### US-09（Must）注文したプロテインのお届け状況を知りたい
> 購入したユーザーとして、注文履歴で各注文が「注文済み」「お届け中」「お届け済み」のどの段階にあるかを確認したい。なぜなら、いつ手元に届くのか・もう発送されたのかが分からないと不安で、届かない場合に問い合わせるべきかどうかも判断できないから。（デモレビュー RV-17・2026-08-27 追加）

- 追加の経緯: `/prototype` のデモレビューで、注文履歴に「お届け状況も合わせて表示したい」という指摘（RV-17）があり、**要件の漏れ**として追加した。
- 補足: モックのため配送業者との実連携は行わない（状況の表示まで）。状況をどう更新するか（管理画面・外部連携など）は `/design` で検討する。

## 3. スコープ外（やらないこと）

| # | やらないこと | 根拠 |
|---|-------------|------|
| 1 | ネット通販・決済サービスとの実連携（Shopify・Stripe・e コマース API など） | Q-01, Q-05 |
| 2 | 実在の個人情報・支払い情報の入力・保存（入力を誘導する機能も作らない） | Q-02, Q-05 |
| 3 | アカウント登録・ログイン | Q-09 |
| 4 | 複数商品を横に並べる比較機能 | Q-10 |
| 5 | 実在商品データの正確性保証（価格・成分はサンプルデータ） | Q-11 |
| 6 | ネット上の情報のスクレイピングによるデータ収集 | Q-07 補足 |
| 7 | 実際のメール送信・電話発信（お問い合わせは連絡先の表示まで） | Q-04 の解釈 |
| 8 | 検索結果・一覧の条件絞り込み機能（複雑になるため） | Q-13 |
| 9 | 配送業者との実連携・追跡番号による自動追跡（お届け状況は表示まで） | US-09 の補足 |

## 4. 後工程への申し送りメモ（How は後工程で決める）

- おすすめの計算方式（外部 AI API ／ ローカルのルールベース計算）: `/design` で決定。モック段階の AI 推奨はローカル計算（questions.md Q-07 の AI 補足）。
- おすすめのカード／カルーセル表示などの UI/UX: `/prototype` でデモを見ながら確定し `ui-spec.md` に記録。
- 注文のデータベース保存（PostgreSQL への言及あり）: `/design` で確定。
- 実データ化する将来フェーズのデータ入手元: 今回のスコープ外。questions.md Q-11 の AI 補足を参照。
