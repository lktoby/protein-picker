### Q-01 送料は「注文 1 件につき 1 回」か「商品 1 個につき 1 回」か

  - B) **商品 1 個につき 1 回**（現状の暫定設計のまま。数量 2 なら送料 1,000円。合計 = 7,960円）
  - C) その他（自由記述）
- AI の推奨: **A**（実際のネット通販の一般的な扱いに合い、利用者の期待とずれない。「送料込みの総額で比較する」というこのアプリの価値〈`ui-spec.md` §6〉も、注文単位のほうが実際の支払額に近くなる）

**前提: プロトタイプはすでに Git に保存されています。** 現在のリポジトリはブランチ `master` のみで、プロトタイプ一式（`src/app/prototype/`）とレビュー記録（`docs/02-prototype/`）は**コミット `ca865f0`（phase 2）にコミット済み**です。未コミットは今回の設計文書だけです。つまり `/implement` でプロトタイプを削除しても、**コードは履歴から永久に取り出せます**（`git show ca865f0:src/app/prototype/recommend/page.tsx` など）。保存のためにブランチを作る必要はありません。

**`dev` / `prod` という名前への懸念（4 点）:**

1. **名前の意味が衝突します。** `dev` / `prod` は慣習的に「**同じプロダクト**の成熟度・デプロイ先」を表す名前です（`dev` がやがて `prod` になる）。そこに「別プロダクト（プロトタイプ）」と「本実装」を入れると、リポジトリを初めて見た人は必ず「`dev` をマージすれば `prod` になる」と誤解します。
2. **2 つのブランチが永久にマージされません。** 中身が別物なので `dev → prod` のマージは起きません。すると**将来の機能追加をどこに置くか**が決まらなくなります（`dev` に置けばプロトタイプのコードと混ざり、`prod` に直接置けば開発用ブランチが無い状態になる）。
3. **`docs/` が分岐します。** この開発フローは `docs/`（要件 → ui-spec → 設計）が唯一の正とすることで成り立っています。両ブランチが `docs/` を持つと、どちらの `ui-spec.md` が正なのか分からなくなります。**これが一番のリスクです。**
4. **維持コストだけが残ります。** プロトタイプのブランチは更新されないまま残り、依存の脆弱性警告や CI の対象になります。保存目的は履歴で足りているため、得るものがありません。

**AI の推奨: 意図はそのまま、名前と手段を変える。**

| やること | 内容 |
|---------|------|
| ① プロトタイプに**タグを打つ** | `ca865f0` に `prototype-reviewed-2026-08-28` のようなタグを付ける。**タグはチェックアウトできる**ので `git checkout prototype-reviewed-2026-08-28 && docker compose up --build` でデモを再現できます。ブランチと同じことができ、維持コストがありません |
| ② `master` は「本実装だけ」にする | `/implement` で `src/app/prototype/` を削除し、shadcn/ui ベースの本実装を入れる。`docs/` は 1 系統のまま |
| ③（任意）常時動くブランチが欲しい場合 | `archive/prototype` という名前で 1 度 push して以後触らない。`dev` / `prod` より意図が明確です |

なお `dev` / `prod` というブランチ運用そのものは有用ですが、それは**同じプロダクトの開発用・本番用**として使う場合です。プロトタイプの保存とは別の話なので、本実装の運用として必要になったら改めて導入するのが素直です。）
